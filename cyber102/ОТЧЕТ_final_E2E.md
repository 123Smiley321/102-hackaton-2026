# Кибер 102 — подтверждённые результаты E2E

Дата восстановления отчёта: 15.11.2026.

Этот файл восстановлен по фактическому журналу Kimi Claw. Ранее журнал сообщал, что отчёт закоммичен, но ветка `main` его не содержала. Ниже отделены уже наблюдавшиеся результаты от проверок, которые ещё предстоит выполнить. Секреты, access tokens и значения внутренних ключей в отчёт не включены.

## 1. Контур публикаций из `main` — подтверждено журналом Claw

Проверялась четырёхсервисная конфигурация из `main`: PostgreSQL, Backend, Telegram-бот и publication worker.

- Все четыре сервиса поднялись, Backend health check вернул `status=ok`.
- Границы секретов соблюдены: у worker не было Telegram token и Fernet key, у bot — административных ключей.
- Telegram: согласованная публикация появилась в тестовом чате, пришло уведомление, запись появилась в mirror `platform_posts`.
- Перезапуск worker не создал дубль. Повторный internal publish вернул `already_published`; неверный publisher key — HTTP 401.
- Несогласованная публикация (`pending_approval`) получила HTTP 409.
- MAX вернул явную ошибку: HTTP 502 и `publish_unknown`; повторный вызов не обошёл защиту и получил HTTP 409. Фейковой успешной публикации не было.
- Internal notify доставлял уведомления; пустой текст отклонялся с HTTP 422.
- VK: пост появился на стене тестового сообщества; community token хранился зашифрованным в БД.
- Кросспостинг: VK и Telegram опубликовали материал одной задачи, обе записи завершились без дублей.
- Расписание: до наступления `scheduled_at` Backend возвращал HTTP 409; worker ждал, после наступления времени публикация прошла.
- При сетевых обрывах Telegram из WSL2 механика `publish_unknown` и ручного `resolve` сработала. Автоматический слепой retry не использовался.

## 2. Известные ограничения того прогона

- VK comments: VK API вернул error 27 для community token. Для проверки чтения комментариев нужен отдельный VK **user access token** с минимально необходимым scope `wall`. Yandex Cloud API key для VK API не подходит.
- Сценарии «обычный комментарий → draft_reply» и «негатив → escalated» поэтому ещё нужно проверить на живом VK-комментарии. Автоматических публичных ответов система не выполняет.
- Из WSL2 наблюдались временные TLS/ConnectError при обращении к `api.telegram.org`, тогда как с хоста соединение работало. На демонстрации при `publish_unknown` сначала сверять площадку, затем использовать `/api/publications/{id}/resolve`; не повторять отправку вслепую.
- VK token был виден в рабочем журнале. Его необходимо перевыпустить; старое значение нигде не воспроизводится и в репозиторий не переносится.

## 3. AI-интеграция — код готов, живой gate ещё не пройден

Ветка: `ai-agent-integration`. Draft PR: #1. `main` на этом этапе не менялся.

Подтверждено статическими и изолированными проверками:

- В корневой Compose добавлен пятый сервис `ai-agent`; порт `8001` опубликован только на `127.0.0.1` хоста.
- Backend, bot и publications передают `X-Internal-Key` при заданном `AI_AGENT_API_KEY`.
- `OPENAI_API_KEY` выдаётся только ai-agent. Backend, bot и worker не наследуют общий `.env` целиком.
- Ai-agent не получает admin/publisher/Fernet/Telegram/VK secrets.
- Worker contract suite: 9/9 тестов пройдено, включая передачу AI internal key и company-scoped payload для comment reply.
- Backend import, routes и формирование AI auth header проверены.
- Compose secret boundary проверен статически; отправленные файлы сверены с GitHub по Git blob SHA.

Не считать выполненным до фактического запуска:

- полный unit suite `ai_agent/tests`;
- Docker build и health checks пяти сервисов;
- живой YandexGPT request с `LLM_PROVIDER=openai` и `engine`, соответствующим YandexGPT;
- HTTP 401 без/с неверным `X-Internal-Key` и HTTP 200 с верным;
- generation с пустой и непустой KB, две компании без смешивания знаний, comment reply без картинки;
- HTTPS image URL либо явно зафиксированный fallback `null` без выдачи его за успешную генерацию изображения;
- полный Telegram → AI-agent → согласование → worker → Backend → VK/Telegram E2E;
- живой VK comment monitoring после получения подходящего VK user token.

## 4. Протокол следующего прогона

Для каждой проверки фиксировать:

| Поле | Что записать |
|---|---|
| Проверка | Название сценария |
| Окружение | Ветка и commit SHA, без значений env |
| Фактический результат | HTTP code, status, engine, publication ID, внешний URL тестового поста |
| Доказательство | Очищенный короткий лог или screenshot без секретов |
| Итог | PASS / FAIL / BLOCKED |
| Действие | Исправление или владелец блокировки |

Перед сохранением логов удалить Authorization/API keys/Telegram и VK tokens, значения внутренних ключей и секретные URL. Не прикладывать `.env`. После успешного AI gate обновить этот отчёт и рабочую таблицу; снятие draft и merge PR #1 выполнять только после явного подтверждения Данила.
