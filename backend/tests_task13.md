# Проверка задачи №13 — настройка компании

## Перед запуском
1. Применить `migration_task13_company_settings.sql` к существующей PostgreSQL БД.
2. Запустить Backend и открыть `http://localhost:8000/docs`.
3. Для всех `/api/companies` запросов передавать `X-Admin-Key`.

## Сценарии

1. **Создание компании** — `POST /api/companies` с `company_id`, названием, описанием, продуктами, аудиторией, преимуществами и настройками. Ожидается `201` и ответ с внутренним числовым `id` и внешним строковым `company_id`.
2. **Чтение списка** — `GET /api/companies`. Созданная компания присутствует в списке.
3. **Чтение по ID** — `GET /api/companies/{id}`. Возвращаются настройки компании; секреты VK не возвращаются.
4. **Чтение по внешнему ключу** — `GET /api/companies/by-external-id/salavatsteklo_demo`. Находится та же компания.
5. **Обновление части профиля** — `PATCH /api/companies/{id}` с `tone_of_voice` и `brand_guidelines`. Неуказанные поля остаются без изменений.
6. **Площадки** — `enabled_platforms` принимает только `vk`, `telegram`, `max`; неизвестная площадка отклоняется валидацией.
7. **Правила согласования** — `approval_required=true`; `approval_mode` принимает `per_platform` или `all_platforms`.
8. **Аудит** — после создания и обновления появляются записи `company_created` и `company_updated` в `audit_logs`.
9. **Изоляция** — запросы чтения/изменения используют конкретный внутренний `company_id`; нельзя подменять внешний slug внутренним FK.
10. **Доступ** — без корректного `X-Admin-Key` API возвращает `401`.

## Ограничение текущего этапа

В этой итерации реализованы профиль, текстовые настройки бренда, перечень площадок и правила согласования. Загрузка файлов PDF/DOCX и их индексация в RAG должны быть подключены отдельным этапом после согласования контракта с владельцем AI/RAG-модуля.
