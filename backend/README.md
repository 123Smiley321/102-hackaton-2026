# Backend — «Кибер 102», Р1 (Ефимова Арина)

## Реализация задачи №12: Telegram-бот и история диалога

Бот принимает свободно сформулированные поручения, определяет компанию по привязанному Telegram chat ID, сохраняет сообщение пользователя и передаёт AI-агенту контекст компании и последние сообщения текущего диалога.

### Возможности

- `/start` — проверка привязки чата к профилю компании и инструкция по подключению.
- `/help` — краткая инструкция.
- `/history` — последние 10 сообщений текущего диалога.
- Любое обычное текстовое сообщение — создание задачи и передача поручения AI-агенту.
- История диалога хранится в PostgreSQL; последние 12 сообщений передаются AI-агенту.
- Успешная обработка создаёт черновик публикации, сохраняет ответ AI и уведомляет пользователя/ответственного о передаче материала на согласование.
- При ошибке задача получает статус `error`, причина фиксируется в журнале без раскрытия технических подробностей пользователю, а пользователю отправляется уведомление.
- FastAPI и Telegram polling запускаются как отдельные процессы/контейнеры.

## Запуск

1. Установить Docker Desktop и запустить Docker.
2. Скопировать `.env.example` в `.env`.
3. Заполнить `TELEGRAM_BOT_TOKEN`, `ADMIN_API_KEY` и `AI_AGENT_URL`.
4. Запустить PostgreSQL и Backend:

   ```bash
   docker compose up --build -d db backend
   ```

5. Запустить Telegram-бота отдельным профилем:

   ```bash
   docker compose --profile telegram up --build -d bot
   ```

6. Проверить `http://localhost:8000/health` и Swagger `http://localhost:8000/docs`.

### Настройка профиля компании (задача №13)

- `POST /api/companies` — создать профиль компании.
- `GET /api/companies` — получить список компаний.
- `GET /api/companies/{id}` — получить профиль по внутреннему числовому ID.
- `GET /api/companies/by-external-id/{company_id}` — найти профиль по внешнему ключу.
- `PATCH /api/companies/{id}` — изменить только переданные настройки профиля.

В профиле настраиваются описание, продукты, аудитория, преимущества, Tone of Voice, правила бренда, доступные площадки (`vk`, `telegram`, `max`) и режим согласования (`per_platform` — отдельное согласование для каждой площадки; `all_platforms` — одно согласование для выбранного набора площадок). По умолчанию согласование обязательно. Секрет VK при обновлении шифруется и никогда не возвращается в API-ответе. Все изменения профиля фиксируются в `audit_logs`.

Для уже созданной БД перед запуском применить `migration_task13_company_settings.sql` один раз. Миграция добавляет настройки компании и не меняет таблицы `publications` / `platform_post`, которыми владеет Данил.

Пример изменения настроек:

```http
PATCH /api/companies/1
X-Admin-Key: <ADMIN_API_KEY>
Content-Type: application/json

{
  "tone_of_voice": "Экспертный, спокойный, деловой",
  "enabled_platforms": ["vk", "telegram"],
  "approval_required": true,
  "approval_mode": "per_platform"
}
```

### Сопоставление company_id между модулями

`company_id` из пакета Лизы сохраняется в `companies.external_id` без преобразования (например, `salavatsteklo_demo`). В API создания компании принимаются оба имени поля: `company_id` и `external_id`. В ответе API возвращаются:
- `id` — внутренний числовой PK Backend; используется в FK `tasks/publications` и совместим с воркером Данила;
- `company_id` и `external_id` — стабильный внешний строковый ключ для AI/контент-модуля.

Backend передаёт AI-agent оба идентификатора: `id` (внутренний int) и `company_id`/`external_id` (строковый ключ). Не заменяйте внутренние FK на строковый ключ. Для поиска профиля по ключу доступен `GET /api/companies/by-external-id/{external_id}`. Для уже существующей БД примените `migration_add_company_external_id.sql` один раз до запуска новой версии.

## Контракт AI-агента

Backend отправляет POST на `AI_AGENT_URL`:

```json
{
  "prompt": "Подготовь пост о продукте",
  "company": {
    "id": 1,
    "name": "...",
    "description": "...",
    "tone_of_voice": "...",
    "products": "...",
    "target_audience": "...",
    "advantages": "..."
  },
  "history": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```

Ожидаемый ответ:

```json
{"text": "Текст публикации", "image_url": "https://example.com/image.jpg"}
```

`image_url` необязателен. При ошибке HTTP или некорректном ответе агентского сервиса задача отмечается как `error`, ошибка записывается в аудит, пользователь получает уведомление.

## Текущие ограничения / следующие задачи

- Обработчик `approve` только фиксирует согласование: устанавливает `status=approved`, `approved_by` и `approved_at`. Он не вызывает API VK/Telegram.
- Модуль публикаций Данила забирает одобренные строки из общей таблицы `publications` (опрос каждые 15 секунд, блокировка строк через `FOR UPDATE SKIP LOCKED`) и отвечает за фактическую отправку, повторы и статусы доставки.
- Для кросспостинга используется отдельная строка `publications` на каждую площадку; поле `platform` определяет целевую площадку. `idempotency_key` должен быть уникальным для каждой такой строки.
- Для существующей БД перед запуском применить `migration_add_approved_at.sql` и `migration_add_company_external_id.sql`: `Base.metadata.create_all()` не добавляет новые столбцы в уже созданные таблицы.
- Кнопка «Доработать» пока только подсказывает пользователю отправить комментарий; полноценный цикл повторной генерации и повторного согласования относится к задаче №16.
- Планировщик, кросспостинг, MAX, статистика и мониторинг комментариев — отдельные задачи команды.
- Административные API пока используют общий `X-Admin-Key`; для коммерческого запуска нужны полноценные пользователи, JWT/RBAC и проверки доступа.
- Для существующей БД `create_all` не меняет структуру уже созданных таблиц; при последующем изменении схемы нужно добавить Alembic migrations.

## Задача №16 — согласование публикаций

- После генерации Backend создаёт отдельную запись `Publication` для каждой включённой площадки компании.
- В Telegram ответственному отправляются текст/изображение, название площадки, плановое время (или «сразу после одобрения»), номер версии и кнопки «Одобрить», «Отклонить», «Доработать».
- Одобрение переводит запись в `approved`; только этот статус разрешён для публикационного воркера.
- Отклонение переводит запись в `rejected`; публикационный воркер не должен её забирать.
- «Доработать» запрашивает комментарий через ForceReply, отправляет исходный текст и комментарий AI-агенту, сохраняет новую версию и повторно отправляет её на согласование. После изменения предыдущий approve сбрасывается.
- При `approval_mode=per_platform` каждая площадка согласуется независимо. При `approval_mode=all_platforms` воркер получает публикации только после одобрения всех площадок одной задачи.
- Callback проверяет, что действие поступило из чата согласования компании.

Перед запуском применить `migration_task16_approval_workflow.sql`. Существующие таблицы автоматически обновлять через `create_all` нельзя: для уже созданной БД обязательна миграция.

### Статусы согласования

`pending_approval` → `approved` / `rejected`; для режима `all_platforms` промежуточный статус `approved_waiting`; при запросе изменений — `revision_requested`, после генерации новой версии — снова `pending_approval`. Воркер публикаций должен выбирать **только** `status = 'approved'`.
